Part 2

How I'd build it

Two phases. The first gets every contract signed electronically and needs nothing from Dropbox Sign beyond the paid plan. The second adds signing inside the tool once Dropbox Sign approves the app.

Phase A · at launch

Email signing, fully automatic status

  • Send for signature, buyer then Fremont Makers, both by email.
  • Tracker, reminders, cancel and resend.
  • Contracted only on Dropbox Sign's verified "all signed" message.
  • Signed PDF and audit trail saved to Documents.
  • Change orders through the same path.
  • Paper upload stays as the fallback.
Needs: paid API plan, API key on the server, callback URL.
Phase B · after app approval

Signing inside the tool

  • Sign here now: the buyer signs on a tablet at the showroom or a site visit.
  • Countersign now: the Fremont Makers signer signs without leaving the tool.
  • Optional "check, then send" view to adjust the message before it goes.
Needs: an API app for fremontmakers.com, approved by Dropbox Sign for embedded signing; its client ID; the signing frame allowed in the page's security settings.

How the pieces talk

Project Builder page

  1. Ready check
  2. Press Send
  3. Shows the tracker
Never sees the API key.

Our server

  1. Renders the packet PDF
  2. Calls Dropbox Sign
  3. Saves request ID on the job
  4. Logs who sent it

Dropbox Sign

  1. Emails the buyer
  2. Collects signatures in order
  3. Posts an event at each step

Callback → job

  1. Verify the event
  2. Update status, log it
  3. Fetch and store the signed PDF
  4. Reply "Hello API Event Received"

Server endpoints

All under the new tool's address, behind employee sign-in except the callback, which Dropbox Sign calls and the server verifies. (These replace the /api/fm/contracts/… names in HANDOFF §16, to match /api/projectbuilder/files.)

EndpointWhat it doesDropbox Sign call
POST /api/projectbuilder/esign/sendSend a contract or a change order. Body: job code, what (contract or change order N), mode. Runs the ready check again on the server first.signature_request/send (A) · create_embedded (B)
POST /api/projectbuilder/esign/remindSend reminder to whoever is next.signature_request/remind/{id}

POST /api/projectbuilder/esign/sign-urlPhase B. Get a one-time signing link when someone clicks Sign here now / Countersign now.embedded/sign_url/{signature_id}
POST /api/projectbuilder/esign/callbackPublic. Receives every event, verifies it, updates the job, fetches the signed PDF.(Dropbox Sign calls us)

The callback, done right

  • Verify every event. event_hash must equal HMAC-SHA256 of event_time + event_type using the API key. Reject anything else.
  • Always answer HTTP 200 with the body Hello API Event Received, or Dropbox Sign keeps retrying.
  • Ignore repeats and strays. Events come more than once and out of order; applyEvent already handles this. Match on metadata.fm_job_code and the request ID.
  • Save the raw event for a year, so any dispute can be traced.
  • Don't do slow work inline. Reply first, then fetch the PDF in the background.

The PDF that gets signed

  • The packet is HTML today. The server prints it to PDF with headless Chrome, using fm-phase1-print.css, so what's signed matches what the team sees.
  • Text tags (FMContract.TAGS) sit invisibly on the signature lines; use_text_tags and hide_text_tags are on.
  • Store the exact PDF that was sent and its SHA-256 with the request, plus a contract version number.
  • After signing, store Dropbox Sign's signed copy beside it. Both stay; nothing is overwritten.
